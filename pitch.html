Ship plan

How I'd ship Cortex

The autonomy dial per segment, where it sits on the trust ladder, how it deploys, what it returns, and how I keep it safe.

01 · Dial

Autonomy per segment

SegmentAutonomyWhy
Seasoned PMBounded-autonomousTrusts Cortex's grounding, can sanity-check a draft in seconds
New/junior PMSupervisedCan't yet tell if a draft is quietly wrong
Exec / stakeholderSupervisedLeast first-hand context to catch a grounding error
EngineersSupervisedNeed to interact directly with the underlying data
02 · Ladder

Rung + eval gate

  • Current rung: Supervised — Cortex owns the entire loop (pulling data, drafting, critiquing, revising), but every run ends either escalated or “queued for your review”; zero ability to post anything on its own.
  • Eval gate to bounded-autonomous: ≥95% EV-1 (tool-call accuracy) pass rate AND 100% EV-5 (safety/jailbreak) pass rate, over the most recent 4 weeks (or last 50 runs) of supervised use.
  • Clean incident record: 0 wrong-project citations reaching a human-approved update, 0 jailbreak-induced policy violations, 0 confidential (Orbit/Pulsar) leaks.
03 · Deploy

Where it runs & who owns it

  • Runtime: Serverless (triggered by the inbound request) — fits the M2 Hook loop type; no always-on server needed.
  • Operator / on-call: Reacher. Escalation path: repeated bound trips or a model-down situation page Reacher directly.
  • Rollback: Revert the prompt/version via git, disable a specific tool (pull it from the TOOLS registry), or drop a segment's dial back a rung.
  • Monitoring: Eval pass % (EV-1–6), escalation rate, cost-to-serve ($0.0006–$0.0048/run observed), trust incidents.
04 · ROI

Value, not activity

MetricTarget
Outcome% of weekly updates approved with no major edits needed
Cost-to-serveAverage $/run, tracked by the Bounds class
Trust incidents# of wrong-project citations, invented metrics, or leaks caught per month
Widen-autonomy rule: once a segment's runs meet the eval gate above with zero trust incidents, it moves up one rung — starting with the seasoned-PM segment.
05 · Governance

How I keep it safe

  • Compliance: CONFIDENTIAL roadmap items (Orbit, Pulsar) can enter Cortex's own context but must never appear in external/company-wide output — an output rule, not an input rule. Real PII/payment/legal data never enters a prompt at all.
  • Safety: Post/approve company-wide, commit a GA date, mark a launch gate — stays above the line for every segment regardless of rung. Kill switch: human manually revokes the OpenAI API key.
  • Reliability: Caps from M5 (iteration 8, revision 2, cost $0.10/run + $0.03/day, queue 10). Model-down fallback: retry twice, pause 2 minutes, retry once more, then escalate to Reacher.
  • Strategy: Widen the seasoned-PM segment to bounded-autonomous first, gated by the Trust Ladder's eval numbers.
Build insights

What I learned

The honest four: where it hurt, what clicked, and what I'd change.

😵 Friction

The validator (critic) was the toughest part of the build — tuning its checks, revision cap, and watching it reject drafts for subtle reasons (an invented risk-level, a conflated project, a stale metric) across nearly every real run took more iteration than any other piece.

🧠 Learning

  • The agent can be dialed to fit different personas (the Autonomy Dial per segment), not one global trust setting.
  • The agent can be fine-tuned to meet specific project objectives rather than running on generic defaults.

💡 Aha

Having multiple agents each do one specific task, instead of one main agent trying to do everything, would likely be more robust than the single-drafter-plus-critic design Cortex ended up with.

🔄 What I'd change

Start with who Cortex is for and what problem is actually being solved for them (the user segments and their needs) before building out the mechanics — that would have saved real cycle time spent fine-tuning its behavior later.
